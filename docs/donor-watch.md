# Сторож доноров ИИ (donor watch)

Следит за донорами — нодами, через которые профили Remnawave выпускают Claude, Gemini,
ElevenLabs, TikTok и OpenAI (socks-аутбаунды `ai-claude`, `ai-gemini`, `ai-out`… →
вход `AI-CASCADE-IN`, mixed, порт 10443, логин/пароль). Если донор умер, сторож
переключает аутбаунд на живого донора, а потом возвращает его обратно.
**По умолчанию работает сухой прогон: только журнал и Telegram, профили не меняются.**

Код:
- `backend/app/services/donor_probe.py` — сеть: SOCKS-рукопожатие, один запрос к сервису через curl_cffi (chrome), SSH-прыжок, чтение фаервола.
- `backend/app/services/donor_watch.py` — логика: реестр, здоровье, решения, сравнение-и-замена конфига, хранение.
- `backend/app/services/donor_watch_runner.py` — цикл, PATCH, сверка после PATCH, журнал незавершённого переключения.
- `backend/app/api/donor_watch.py` — `/api/donor-watch/*`.
- `backend/tests/test_donor_watch.py` — 41 тест.

## Как устроено

**Реестр.** Каждый цикл читает (только GET) `/api/nodes` и `/api/config-profiles/{uuid}`.
- *Привязка* — пара «профиль + тег аутбаунда». Сервисы привязки берутся из правил routing (по `outboundTag`).
- *Донор* — адрес и порт: из socks/http-аутбаундов на порт 10443 или на адрес из реестра, а также из профилей с входом `AI-CASCADE-IN`. Логины к нему берутся оттуда же и хранятся только в памяти.
- Ручной список `donors` задаёт имя, ноду панели, флаги `retired`/`disabled` и преемника.
- Уже внесены fi-2 151.241.229.200, старый fi-2 194.180.189.133 (`retired`, преемник fi-2), de-cdn-yandex, Париж, fi-cdn-yandex, fi-timeweb и fi-AI.
- Сторож замечает:
  - смену IP донора: адрес ноды в панели не совпал с реестром;
  - ссылку на списанный адрес;
  - ноду донора, пропавшую из панели;
  - привязку без распознанных сервисов.

**Проверка** выполняется раз в `interval_min` (не меньше 20 мин).
- Доноры перебираются в случайном порядке и разнесены по окну `spread_s` (по умолчанию 240 с).
- На каждого донора: одно SOCKS-рукопожатие, затем ровно один лёгкий запрос на сервис. Между запросами пауза 4–12 с.
- Запросы по сервисам:
  - Claude — `GET api.anthropic.com/v1/models`;
  - OpenAI — `/v1/models`;
  - Gemini — 5-токеновый запрос с ключом из «Доступности приложений», без ключа — только доступность `ai.google.dev`;
  - ElevenLabs — главная страница без редиректов;
  - TikTok — `/login`.
- Как трактуется ответ:
  - тишина до таймаута — мёртв;
  - челлендж Cloudflare (403) — жив;
  - гео-блок — мёртв.
- Провал подтверждается повторной проверкой через `recheck_delay_s` (90 с плюс случайные 0–30 с). Мёртвым считается только двойной провал. Если повтор прошёл успешно, донор жив, но счётчик живых циклов обнуляется.

**Откуда стучимся.** Порт донора закрыт allowlist-ом, а IP рагента в нём, скорее всего, нет.
- Поэтому запрос идёт через SSH-прыжок на ноду из рагента: paramiko `direct-tcpip`, локальный мост, curl_cffi `socks5h://`.
- Порядок выбора прыжков:
  1. `probe_hops` из настроек;
  2. прыжки, которые уже срабатывали;
  3. ноды-потребители донора, которые есть в allowlist.
- `probe_hops_only: true` — только явный список `probe_hops`, без автоподбора (пункты 2–3).
- `probe_hops_exclude` — ноды, через которые не щупать никогда. **Ноду владельца и ноду, через которую работает ПК оркестратора, вписать сюда обязательно**: пробы не должны идти через неё.
- Нода сопоставляется с рагентом только по IP. Используются не больше двух прыжков. DNS имён нод резолвится в потоке, цикл событий не блокируется.
- «Не достучаться» с одного непроверенного прыжка считается «неизвестно», а не «мёртв».

**Решения** принимаются по каждой привязке.
- Если хотя бы один её сервис мёртв или донор списан, выбирается кандидат. Кандидат должен пройти все проверки:
  - **жив в этом цикле по всем сервисам привязки**;
  - не умирал последние `quarantine_min` минут;
  - не стоит на нодах этого же профиля (иначе петля);
  - allowlist пускает все ноды профиля.
- Allowlist читается с донора по SSH раз в 6 ч, только чтение. Если он не сверен, кандидат годится в двух случаях: профиль уже ходит на этого донора или это родной донор привязки.
- Возврат на родного донора — после `back_after_cycles` (3) живых циклов подряд и не раньше `back_min_gap_min` (60) минут после прошлого переключения.
- Потолки:
  - `max_patches_24h` (24) PATCH на весь парк — хватает на падение fi-2 при 17 профилях;
  - `max_switches_binding_24h` (3) на привязку.
- Профили без включённых нод (вроде TR-RAW-REALITY-ITU, UA-RAW-WRP) не переключаются и потолок не тратят: PATCH впустую. Как только на профиле появится нода, следующий цикл его переключит.
- Порядок профилей детерминированный: сначала с меньшим числом пользователей в сети (`usersOnline` нод профиля), затем по имени. Сбой на первом профиле заденет меньше людей, а потолок тратится в том же порядке.
- «Неизвестно» никогда не ведёт к переключению.

**Переключение** работает только в боевом режиме.
1. Профили обрабатываются по одному и по одному PATCH на профиль, последовательно, в порядке выше.
   Весь цикл укладывается в `cycle_budget_s` (900 с, не больше интервала минус минута): если до конца бюджета не влезает ещё одна сверка (`post_check_s` + 60 с), оставшиеся профили переносятся на следующий цикл. Об этом приходит тревога «не уложился… перенесены: …», в `last_cycle.deferred` — их список.
2. Перед PATCH профиль перечитывается: срабатывает сравнение-и-замена. Если адрес в аутбаунде уже не тот, что видел цикл, правка пропускается.
3. Затем:
   - запоминается uptime нод (панель не отдала ноды — PATCH не делается, профиль и все следующие — в следующем цикле, без остановки);
   - снимается зашифрованный бэкап профиля в `app_settings` (последние 30);
   - пишется запись `pending`.
4. После PATCH профиль перечитывается. Затем 180 с ждём, что все ноды профиля снова подключены и xray перезапустился. Если uptime не сбросился за 60 с, ноде один раз даётся restart через панель.
5. Любая неудача включает **остановку**: halt, уведомление с номером бэкапа и прекращение всех следующих PATCH. Остановку снимают вручную.

## Пограничные случаи

| Случай | Что делает |
|---|---|
| Панель не отвечает | Цикл без решений. Тревога после 2 неудачных чтений подряд |
| Цикл упал с исключением | Время старта цикла пишется в состояние до проб (`cycle_started_at`), после падения — пауза на полный интервал. Пробы не повторяются каждую минуту, в том числе после перезапуска рагента |
| `pending` есть, а до цикла далеко | Раз в ≤5 мин только сверка `pending`, без проб. Пока не сверено, цикл не принимает решений |
| Донор мигает | Нужен двойной провал. Живой повтор обнуляет счётчик. Карантин 60 мин. Возврат только после 3 живых циклов и не чаще раза в час |
| PATCH упал или применился частично | Профиль перечитывается и сверяется. Затем остановка и уведомление с номером бэкапа. Остальные профили этого цикла не трогаются |
| Рагент перезапустился посреди переключения | Запись `pending` разбирается первой в следующем цикле. Если правка в панели — сверка нод и завершение. Если правки нет — остановка |
| Профиль правят руками или другой агент | Сравнение-и-замена не даёт перезаписать чужое. Новый адрес становится «родным» для привязки, это пишется в журнал |
| Сменился IP донора | Тревога `ip_changed`. Новый адрес становится преемником |
| Все кандидаты мёртвы или не сверены | Действие `no_candidate`, только тревога |

Тревоги приходят в Telegram с префиксом «🧩 Доноры ИИ»: при смене состояния и напоминанием раз в `remind_hours`. В сухом прогоне вместо PATCH приходит одно сводное «сделал бы (N): …» на цикл (новое — только если список изменился). Тексты ошибок панели проходят через чистку: токен, логины доноров, поля `pass`/`password`, `Bearer …`.

## Выкатка

1. Проверить, что токен панели в рагенте имеет доступ к разделу config-profiles:
   `GET /api/config-profiles` → 200. Ответ 403 значит, что надо расширить права ключа API в панели. Иначе сторож всё время будет писать «панель недоступна».
2. Проверить, что у нод-прыжков в `sshd` разрешён TCP-форвардинг (`AllowTcpForwarding yes`, по умолчанию так и есть).
3. Собрать и перезапустить API так же, как обычно:
   `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build api`.
   Первый цикл стартует через 2–4 минуты после запуска.
4. Через 30 минут посмотреть `GET /api/donor-watch/status` (подходит Bearer-токен). В ответе:
   - реестр, привязки, состояние сервисов по донорам;
   - `issues`, allowlist-пробелы, журнал.
   Логинов в выводе нет.
5. Несколько суток держать сухой прогон и сверять «сделал бы…» с реальностью.
6. Боевой режим включает только владелец, из браузерной сессии:
   `PATCH /api/donor-watch/settings {"dry_run": false}`.
   Смена режима попадает в журнал и в Telegram.

Прочие ручки (только браузерная сессия):
- `POST /api/donor-watch/check` — внеочередной цикл, не чаще `interval_min`;
- `POST /api/donor-watch/reset-halt` — снять остановку после разбора;
- `PATCH /api/donor-watch/settings` — реестр `donors`, `priority` по сервисам, `probe_hops`, `probe_hops_only`, `probe_hops_exclude`, потолки, `cycle_budget_s` и интервалы;
- `POST /api/donor-watch/restore` — восстановить профиль из бэкапа (см. ниже).

`GET /api/donor-watch/backups` (подходит и Bearer) — список бэкапов: номер, время, профиль, причина. Содержимого и логинов в нём нет.

## Откат

1. Остановить автоматику: `PATCH /api/donor-watch/settings {"dry_run": true}` или `{"enabled": false}`. Остановка (`halted`) после сбоя тоже держит PATCH-и, восстановление её не снимает.
2. Посмотреть, что изменится:
   `POST /api/donor-watch/restore {"backup_id": "<номер из уведомления>"}` — по умолчанию `dry_run: true`, панель не меняется. В ответе `outbounds`: тег, адрес сейчас, адрес в бэкапе, меняется ли логин (сами логины не показываются), и `identical`, если профиль уже такой.
3. Применить: тот же запрос с `"dry_run": false`. Только из браузерной сессии, как и PATCH настроек; во время цикла — 409.
   - Перед PATCH снимается бэкап текущего профиля (`pre_restore_backup` в ответе), так что откат тоже откатывается.
   - Профиль перечитывается, сверяются адреса аутбаундов (`verified_outbounds`). Ноды профиля после восстановления ручка не ждёт — проверить их в панели.
   - Привязки профиля помечаются как стоящие на восстановленных адресах: следующий цикл не примет это за чужую правку, родной донор сохраняется. PATCH считается в суточный потолок.
   - Запись в журнал (`restore` / `restore_failed`) и в Telegram.
4. Разобраться в причине, затем снять остановку (`reset-halt`) или вернуть боевой режим.
